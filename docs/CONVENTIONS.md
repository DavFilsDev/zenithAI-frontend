# Conventions

Rules for this repository. They apply to code and documentation alike. Anything not covered here is settled by judgement, and the decision is written down in the pull request.

## Workflow rules

### Branches

One branch per subject, named after its prefix:

| Prefix | Use |
|---|---|
| `docs/*` | Documentation only |
| `feat/*` | New behaviour |
| `fix/*` | Bug fix |
| `chore/*` | Tooling, dependencies, configuration, refactors with no behaviour change |

Examples: `docs/api-contract-v1`, `feat/streaming-sse`, `fix/refresh-single-flight`, `chore/vitest-setup`.

A branch carries one subject. Unrelated changes are split into several branches, so each one can be reviewed and reverted on its own.

### Commits

- **Only the human commits.** Nothing else stages, commits, pushes, rebases, resets or stashes.
- AI coding agents never run `git add`, `git commit`, `git push`, `git reset`, `git stash`, `git checkout --`, or any history rewriting command. They edit the working tree and report what changed.
- An agent that needs a new branch asks for it, and stops there.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): subject`, lowercase, imperative, no trailing period, one logical change per commit.
- Allowed types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`.
- Subject line under 72 characters. The body explains the reason for the change when it is not obvious from the diff.

### The API contract

- [`docs/API_CONTRACT.md`](API_CONTRACT.md) is read **before** any change that touches the API: base URL, routes, methods, payloads, status codes, error codes, pagination, authentication, streaming.
- The contract is shared with the backend repository. Both copies stay identical. A change lands in both, in the same release.
- Anything the contract does not describe is not part of the API yet. A call the frontend makes today on a legacy path is a migration item, not a convention.
- The OpenAPI schema generated by the backend describes what exists there, and never contradicts the contract without an explicit note.

### Comments

- No comment unless it explains a non-obvious *why*. Never a *what*: the code says what it does.
- No decorative comments, no section banners, no commented-out code.
- No JSDoc that only restates the name of a function or a prop. A doc comment is allowed when it explains a constraint, a non-obvious side effect, or a decision that would otherwise look wrong.
- Rules from React, Vite or TypeScript itself do not need to be repeated in the code.
- One line per comment, written in English, ending with a period only if it is a full sentence.

## React and TypeScript conventions

### Structure

Organised by feature, not by kind. A feature owns its components, its hooks, its services and its types:

```
src/
├── app/            router, providers, global error boundary
├── features/
│   ├── auth/       login, register, session, profile
│   └── chat/       conversation list, message list, composer, stream
├── shared/
│   ├── api/        client, interceptors, error type
│   ├── ui/         Button, Input, Modal, Toast
│   └── lib/        pure helpers
└── main.tsx
```

- Import order: React and libraries, then `shared`, then `features`, then local files, separated by blank lines.
- A feature never imports from another feature's internals. Shared code is promoted to `shared/` or the rule is written down.
- Files are named after what they export: `useConversations.ts`, `ConversationList.tsx`, `apiClient.ts`. No `index.ts` barrels except the public entry of a feature.

### Components

- Function components only. `React.FC` is not used; the props type is declared and exported next to the component.
- One component per file, except a `*.stories.tsx` or a colocated `*.test.tsx`.
- Props are declared with `interface XxxProps` for component props and `type Xxx = {}` for data shapes.
- Derive state instead of storing it. Two pieces of state that must change together are one state.
- An effect synchronises with something outside React. It is never used to compute a value that could be computed during render.
- Every list has stable keys. The index is only a key for a list that never reorders.
- Conditional rendering uses `&&` or a ternary, never a `0` or an empty string as the condition.

### Hooks

- `useXxx` for custom hooks, `useXxxQuery` for server state once TanStack Query is adopted, `useXxxStore` for a Zustand slice selector.
- A custom hook returns a value or an object of named values, never an array of mixed types.
- Every effect that subscribes to something returns its cleanup.
- A hook that fetches returns `{ data, isPending, error, refetch }` and nothing else, so a component never branches on three different shapes.

### State

Three kinds, never mixed in one component:

| Kind | Lives in | Examples |
|---|---|---|
| Server state | TanStack Query | conversations, messages, profile |
| UI state | Zustand | sidebar open, active theme, composer draft |
| Local state | `useState` | input value, field being edited |

- Zustand stores are sliced by feature, one `useXxxStore` per slice, and selected field by field. A component never subscribes to the whole store.
- Nothing is persisted to `localStorage` unless it survives a reload by design, and the list of persisted keys is short and explicit. Conversation content is not persisted.
- Context is used for what a subtree needs but a hook cannot reach: theme, session bootstrap. Not a state manager.

### Forms

- `react-hook-form` for every form, with an explicit `zod` resolver once `zod` is adopted.
- Field errors are read from the form state, never from an API response mapped onto inputs by hand.
- The submit button is disabled while submitting and the request is not fired twice.

### API

- One Axios instance for the whole app, in `shared/api/`. No component, hook or page calls `axios` directly.
- The base URL comes from `import.meta.env.VITE_API_URL` and from nowhere else. No path prefix is hardcoded in a call.
- The `Authorization` header is attached by the request interceptor, never by a caller.
- Token refresh is single-flight: one refresh in flight, every waiting request replays after it.
- Every error is normalised to one error type carrying `status`, `code`, `message` and `details`, and every caller branches on `code`, never on a raw status number.
- `PATCH` is used for partial updates, and only for the fields the contract allows.

### Types

- `strict` is on and is actually enforced, including `noUncheckedIndexedAccess`.
- No `any`. When a third-party type is wrong, the boundary is narrowed by hand, in one place.
- `import type { X }` for type-only imports, required by `verbatimModuleSyntax`.
- Enums are avoided, `erasableSyntaxOnly` is on. A closed set of strings is a union type.
- The environment is typed once, in a `vite-env.d.ts` that validates the shape of `import.meta.env`. An unset variable is a startup error, not a `undefined` that fails later.
- `unknown` in a `catch` clause, narrowed before use.

### Styling

- Tailwind only, v4, configured in CSS with `@theme`. There is no `tailwind.config.js` and no CSS Modules.
- Design tokens are referenced through the theme, never as a raw arbitrary value such as `bg-[rgb(var(--color-primary))]`.
- A value used in more than three components is a token. A value used once stays inline.
- Conditional classes are composed with a helper or a template string, never string-concatenated into a variable.
- Colours that differ between themes are driven by the token, not by a `dark:` variant hardcoded per component.

### Tests

- Vitest with Testing Library, and MSW for the network. A test never mocks a module that talks to the API.
- Naming: `describe('<unit>')` / `it('returns the paginated conversations')`. A test name states the expected outcome, not the function name.
- Every user-visible flow has at least one test: sign in, send a message, read a rate-limit error.
- Accessibility is asserted where it matters: `getByRole` over `getByTestId`, and no test id that exists only to make a selector work.
- Playwright covers two or three end-to-end journeys only. Anything more belongs in a unit or integration test.
- Coverage target: 80% on `features/` and `shared/api/`, measured, enforced in CI.

### Accessibility

- Every interactive element is a real `button`, `a` or `input`. A `div` with an `onClick` is a bug.
- Every icon-only control has an `aria-label`. A control that toggles has `aria-expanded` or `aria-pressed`.
- Every input has a `label` bound with `htmlFor` to a matching `id`, and an error linked with `aria-describedby` and announced.
- Anything that appears or updates asynchronously is inside an `aria-live` region: the streaming answer, the loading state, a toast.
- A modal has `role="dialog"`, `aria-modal`, a labelled title, a focus trap, `Escape` to close, and focus restored to the trigger.
- Animation is disabled under `prefers-reduced-motion`.
- Landmarks exist on every page: one `main`, a `header` when there is one, `nav` for navigation lists.

### Naming

- Components, types and interfaces: `PascalCase`. Hooks: `useXxx`. Everything else: `camelCase`.
- Files match the export: `MessageBubble.tsx`, `useConversations.ts`, `apiError.ts`.
- Booleans read as a predicate: `isLoading`, `hasMore`, `canSend`.
- Event handlers: `handleX` for a local function, `onX` for a prop.
- Environment variables: `UPPER_SNAKE_CASE`, prefixed `VITE_`, declared in `.env.example` in the order they are read.

### Git and pull requests

- A pull request describes what changes for the user, and what does not change. Breaking API changes are listed explicitly.
- A pull request that changes an API call updates [`docs/API_CONTRACT.md`](API_CONTRACT.md) in the same commit set, and states that the backend copy must be updated too.
- A pull request that changes the roadmap in [`docs/IMPROVEMENT_PLAN.md`](IMPROVEMENT_PLAN.md) ticks the box it completed, in the same commit.
